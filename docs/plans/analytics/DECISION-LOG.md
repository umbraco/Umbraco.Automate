# Decision log

- **06-11-2026 (feature-explore, with user):** Target v19 only, with no v18 or v17 version. Analytics UI only exists for CMS 19, and building a second set of charts for the older lines would double the frontend work for a feature with no deadline.
- **06-11-2026 (feature-explore, with user):** Use Analytics UI rather than Automate's own charts, to match Engage, Commerce, AI, Forms and Workflow.
- **06-11-2026 (feature-explore, with user):** Kill criteria: queries that are too slow on a large site, or a finding that a few more numbers on the Overview dashboard would be enough.
- **06-11-2026 (feature-explore):** Plan folder lives in the `v19/dev` worktree (`.claude/worktrees/v19-dev`), not on `v18/dev`, because the feature is built on the v19 line.
- **06-11-2026 (feature-explore, with user):** The first version is the run trend, headline numbers, an automations table and an actions table. Approvals, runs by hour of day, step reach and runs by trigger wait, to keep the first version small while there's no deadline.
- **06-11-2026 (feature-explore, with user):** Leave out numbers Automate doesn't store (rate-limit rejections, outbox throughput, failures per connection). Storing them is a separate feature with its own migration.
- **06-11-2026 (feature-explore, with user):** "Too slow" means a chart or table over 2 seconds on SQL Server with 500,000 runs in 90 days. That makes the kill criterion something design can test.
- **06-11-2026 (feature-explore, with user):** The Overview dashboard stays as it is and gets a link to Analytics. Restyling it would widen the feature for no new information.
- **06-11-2026 (feature-design, with user):** Analytics is a sidebar menu item opening its own workspace (Umbraco.AI's pattern), not a fourth dashboard tab. Later views become tabs on that workspace without moving anything.
- **06-11-2026 (feature-design, with user):** Count live from the run tables with new indexes, not a daily summary table. A seeded 500,000-run speed test is the first build task; a summary table is the fallback, behind the same service interface.
- **06-11-2026 (feature-design):** The Overview dashboard is not enough on its own (the brief's kill criterion). It has no date range, no trend, and nothing per automation or per action, and adding those would turn it into this page. It gets a link instead.
- **06-11-2026 (feature-design):** Rejected runs count as successes, matching `GetRunCountsByAutomationAsync`. Note that `RunSummary.SuccessRate` (used by nothing in the UI today) counts only Completed, so the two disagree.
- **06-11-2026 (feature-design):** The server groups by UTC quarter hour and the service folds those into the user's local days. Hour groups would misplace runs in +05:30 and +05:45 time zones, and EF can't convert time zones on both databases.
- **06-11-2026 (feature-design):** Action names are resolved in the browser from the catalogue, like the run views, so actions from an uninstalled package still show by alias.
- **06-11-2026 (feature-design, with user):** Approved all nine design guesses: `DurationMs` column for the median, a Monitoring menu, a workspace select rather than a picker, week and month summed in the browser, presets 7/30/90/custom up to 366 days, no hourly chart, client-side tables, only the approvals tile links, and the workspace select hidden for single-workspace users.
- **06-11-2026 (feature-design, with user):** Automations and actions stay as two separate boxes, not one Breakdown box with a toggle. Their columns differ, and both should be visible without switching.
- **06-11-2026 (feature-plan):** The speed test (T4) runs at repository level, straight after the queries exist, and gates everything else. Endpoint-level timing is re-checked at the API wire task (T9). Building the controller and the UI first would waste them if the live-query approach fails.
- **06-11-2026 (feature-plan):** The speed test is opt-in (`AUTOMATE_PERF_SQLSERVER`, `Category=Performance`) and runs on LocalDB, not in CI. The repo has no SQL Server test host, and seeding 1,000,000 runs on every build isn't worth it.
- **06-11-2026 (feature-plan):** It seeds 180 days with run cleanup off, so the 90-day comparison is really counted. With the default 90-day retention, the comparison would be dropped (R7) and the test would only time half the work.
- **06-11-2026 (feature-plan):** Pending C# specs are wrapped in `#if AUTOMATE_ANALYTICS`, because they're written against types that don't exist yet. The alternative, empty placeholder bodies, would lose the arrange and assert that make them worth writing.
- **06-11-2026 (feature-plan):** Analytics UI is pinned to the MyGet nightly (`19.0.0--alpha.1.preview.275.g7fa295d`, npm by tarball URL) until 19.0.0 is public. The planned `[19.0.0, 19.999.999)` range can't admit a prerelease below 19.0.0, and an `.npmrc` scope would send every `@umbraco/` package to MyGet. T20 swaps in the range.
- **06-11-2026 (feature-plan):** The page's specs are Playwright acceptance specs, not component tests. The client has no component test harness, and the acceptance suite is already how Automate's backoffice is tested.
- **06-11-2026 (feature-plan, with user):** Plan approved as written: 20 tasks, T4's speed test gating everything after it, 96 pending specs.
- **06-11-2026 (feature-build T1, with user):** Runs that stuck-run recovery marks as Failed (interrupted by a restart) get no `DurationMs`, and the backfill skips them too. Their elapsed time includes the downtime and would skew the median. They still count as failed runs.
- **06-11-2026 (feature-build T1):** Interrupted runs are recognised in the backfill by `Status = 3` and an `Error` starting "Recovered after application restart". No column marks them, and a migration can't reference the private `InterruptedError` constant. The text dates from #359 and every existing interrupted row carries it, so a later rewording can't affect this one-off backfill.
- **06-11-2026 (feature-build T1):** The EF 11 tooling regenerated both model snapshots in its own style: a file-scoped namespace, `ToTable` without a schema argument, `LastMigrationId`, and ProductVersion 11.0.0-rc.3. The reviewer confirmed the only model changes are `DurationMs` and the two indexes. Every later v19 migration would cause the same churn.
- **06-11-2026 (feature-build T1):** Generated migration classes were renamed from `_<timestamp>_UmbracoAutomate_AddRunAnalytics` to `UmbracoAutomate_AddRunAnalytics`, to match the existing migrations. The `[Migration]` ids are unchanged.
- **06-11-2026 (feature-build T2):** The median of an even number of runs is the average of the two middle values (integer milliseconds). It costs the same as taking one value: a count, then 2 rows with OFFSET/FETCH.
- **06-11-2026 (feature-build T2):** Per-automation aggregates always join automations, even unscoped, because each row needs the automation's current name and workspace. The other queries skip the join when unscoped. They agree because deleting an automation deletes its runs first (`AutomationService.DeleteAutomationAsync`).
- **06-11-2026 (feature-build T3):** For an action, a finished step is Completed, Failed or Rejected. A Cancelled step counts as a run but not toward the average time or the failure rate. A step is only cancelled when it was waiting for approval and someone stopped its run, so its time is mostly waiting and would skew the average. This differs from runs, where R4 counts a cancelled run as finished, and reads as SPEC R5's "finished" for actions.
- **06-11-2026 (feature-build T3):** A failed step with no error category counts under Unknown, which the page shows as Other.
- **06-11-2026 (feature-build T3):** Average step time is `double?`, cast to float in SQL, like the run average. Averaging a bigint doesn't behave the same on SQL Server and SQLite.
- **06-11-2026 (feature-build T4, with user):** The speed gate first failed (summary 3.45 s, actions 4.47 s). The user approved one tuning round, which brought summary to about 1 s, actions to about 1.2 s and automations to about 0.3 s, all workspaces on LocalDB. The tuning: actions in one grouped scan per range, the median count taken from the grouped summary query, and current and comparison ranges in parallel.
- **06-11-2026 (feature-build T4):** The analytics service (T5, T6) must run the current-range and comparison-range queries in parallel, each on its own DbContext, as the speed test does. Run one after the other, actions could take about twice as long, over 2 s.
- **06-11-2026 (feature-build T4):** Known limit: actions for one workspace took 1.8 s and 2.2 s on LocalDB (SQL Server Express). That's the step-to-run join for scoping. AN-1's target is all workspaces, so this isn't gated. If it matters later, scope step runs through the run's own `WorkspaceId` snapshot, which would mean revisiting the T3 rule of using the automation's current workspace.
- **06-11-2026 (feature-build T4):** The quarter-hour groups and the median come from one repository call, which counts the median's population itself. Two overloads that only work if the caller passes a matching count were rejected on review.
- **06-11-2026 (feature-build T4, with user):** The speed gate is judged on full SQL Server (Developer edition, median of 5 runs) as well as LocalDB. LocalDB is SQL Server Express, capped at 1 GB of memory with no parallelism, so it was noisy and hid a plan problem that only full SQL Server showed.
- **06-11-2026 (feature-build T4):** The exact median is found by narrowing duration buckets (widths of 1,000,000, 10,000, 100 and 1 ms). Grouped counts find the bucket holding the middle values, and only that bucket's rows (at most 10,000) are sorted. This replaces the T2 entry's "a count, then 2 rows with OFFSET/FETCH", which spilled to tempdb on full SQL Server. The result is unchanged: the average of the two middle values for an even count.
- **06-11-2026 (feature-build T4):** Negative run durations, which only clock skew between servers can cause, are left out of the median and of the per-automation average. Both use the same set of runs (SPEC R5).
- **06-11-2026 (feature-build T5):** The public analytics models (`AnalyticsQuery`, `AnalyticsSummary`, `AnalyticsPeriod`, `AnalyticsDay`) use `init` properties, not positional records, like the existing `RunSummary`. A positional record can't gain a member inside a major without breaking its constructor and `Deconstruct`.
- **06-11-2026 (feature-build T5):** `retainedFrom` is null unless age-based cleanup actually runs (`RunCleanupPolicy.Enabled` and `RetentionDays > 0`). It's the first fully kept day, today − RetentionDays + 1, because cleanup deletes by the exact time of day. Count-based cleanup (`MaxRunsPerAutomation`) can also delete newer runs, which `retainedFrom` can't show; that's accepted as a limit.
- **06-11-2026 (feature-build T5):** Dates at the edges of the calendar (e.g. 9999-12-31) are refused by the T8 controller with a 400, not by the service, so R10's statuses stay as specified.
- **06-11-2026 (feature-build T6):** Workspace names come from one `GetAllWorkspacesAsync` call per request, and only when there are rows. `IWorkspaceService` has no lookup by a set of ids, and workspaces are few. Only names of workspaces already in the scoped rows reach the output.
- **06-11-2026 (feature-build T6):** A row whose workspace no longer exists shows an empty workspace name, since SPEC's `workspaceName` is a non-nullable string.
- **06-11-2026 (feature-build T6):** Average run times are whole milliseconds (`long?`, rounded), like the median. Action averages are converted from ticks.
- **06-11-2026 (feature-build T7):** The shared scoping helper takes its services as parameters and is `private protected`, rather than the base class gaining a constructor. `MetricsControllerBase` shipped in 18.x with an implicit parameterless constructor, and every other base controller in the repo passes services to its helpers, so nothing breaks and the v19 upgrade notes need no entry.
- **06-11-2026 (feature-build T8):** All four analytics dates must fall between 2000-01-01 and 2999-12-31, or the controller answers 400 before calling the service. This keeps calendar-edge dates (e.g. 9999-12-31) from throwing in the day maths. A missing `from`, `to` or `timeZone` gets ASP.NET's automatic 400 through `[BindRequired]`.
- **06-11-2026 (feature-build T8):** The three endpoints share one `[FromQuery]` request model, so adding a query parameter later is one change, not three.
